# Testing the install in a VM

Dry-run `install/install` against a real EndeavourOS install before touching real hardware. A
container is not enough — GRUB, dracut, plymouth and greetd are where the risk is, and none of them
can be tested without a real boot.

## Setup

```sh
sudo pacman -S --needed virt-manager qemu-desktop libvirt edk2-ovmf dnsmasq
sudo systemctl enable --now libvirtd.socket
sudo usermod -aG libvirt $USER
```

Log out and back in for the group to apply, then grab the ISO from
https://endeavouros.com/latest-release/ and open `virt-manager`.

## Create the VM

New VM → Local install media → pick the ISO. Give it 8 GB RAM, 4 CPUs, 60 GB disk.

On the last page tick **Customize configuration before install**, then in Overview set
**Firmware: UEFI**. This is the one setting that matters and the only one that is not the default —
the install scripts rewrite `/boot/grub/grub.cfg` and rely on dracut.

In the EndeavourOS installer:

- **btrfs root**, or snapper and grub-btrfs fail
- **pick a desktop edition**, not the no-DE one. Its login manager is what exercises the greetd
  takeover in `config-login-manager`, one of the things most likely to break.
- same username as the real machine

## Snapshot before installing myarchy

This is the point of the whole exercise — each retry resets in seconds instead of a full reinstall.
In virt-manager, open the VM and use the snapshot icon in the toolbar to create one called `base`.
Same button restores it.

## Run

```sh
git clone https://github.com/Flo-CS/config.dotfiles ~/.local/share/myarchy
MYARCHY_INSTANCE_ID=desktop ~/.local/share/myarchy/install/install
```

Then reboot and work through the checks in [installation.md](installation.md).

If Hyprland refuses to start on the virtual GPU:

```sh
WLR_RENDERER_ALLOW_SOFTWARE=1 uwsm start hyprland.desktop
```

## Passes worth doing

1. **Clean install** from the `base` snapshot, then reboot and check.
2. **Re-run** `install/install` on the installed VM. Nothing should be duplicated: no second Windows
   menuentry, no repeated `AUTOGENERATED` blocks in `/etc/default/grub-btrfs/config`, no re-prompt.
3. **Laptop pass** — restore `base`, run with `MYARCHY_INSTANCE_ID=laptop`, then confirm
   `find ~/.config -xtype l` prints nothing.
4. **Failure recovery** — interrupt a run with ctrl-c, re-run, and confirm it skips the steps already
   listed in `~/.local/state/myarchy/install-steps`.

## Troubleshooting

### Failed to start network default: firewalld can't find the 'libvirt' zone

firewalld loads its zones once at startup. libvirt drops `/usr/lib/firewalld/zones/libvirt.xml` when
it is installed, so a firewalld that was already running never sees it.

```sh
sudo firewall-cmd --reload
sudo virsh net-start default
sudo virsh net-autostart default
```

Removing firewalld fixes it permanently instead — libvirt only looks for that zone while firewalld is
running, and otherwise uses its nftables backend directly.

### VMs start but have no network

ufw defaults `FORWARD` to `DROP`. Set `DEFAULT_FORWARD_POLICY="ACCEPT"` in `/etc/default/ufw`, then
`sudo ufw reload`.

## What a VM cannot tell you

Check these on real hardware only:

- NVIDIA drivers and the per-instance `LIBVA_DRIVER_NAME` vars
- the Windows Boot Manager GRUB entry — `config-grub-menu-entries` finds nothing in a VM
- `config/wireplumber/lg_screen.conf`, which matches a specific monitor
- ultrawide layout and `myarchy-toggle-ultrawide-center`
- battery detection in `config-battery-and-power` — a VM has no battery, so it takes the
  `performance` branch and never enables the battery-monitor timer
